# Current frontend API

The unified primary journey uses strict `POST /api/v1/conversation/turn`. The request contains locale, an enum event, at most two local `{service_id,confidence}` candidates, optional confirmed service ID, one verified readiness answer or completed preparation field ID, optional citizen-confirmed allowlisted document evidence, and bounded public journey state. The state carries completed field IDs and never values. Unknown fields are forbidden. Raw finder text is never sent; arbitrary message text is accepted only for affirmative-consent cloud clarification and is PII-screened again. The response contains the assistant message, next action, safe response actions, active summary, one current readiness or typed preparation question, deterministic readiness/checklist/structural sheet definition, prepared counts, missing required field IDs, contextual official sources, pack-owned handoff, and updated public state. Every response is `no-store`.

The browser keeps conversation history, public graph state, active procedure, readiness answers/labels, authoritative personal prepared-value records, checklist, populated worksheet preview, voice transcript, document work, and progress in React memory. Each prepared value tracks source, confirmation, local validation, editability, and a local update revision. The server has no session/checkpointer/store. Confirmed service/question/answer/document/completed-field IDs are revalidated against the current registry and readiness is recomputed. Checklist and preparation definitions fan out after every interview turn; required local fields delay handoff. No audio, file bytes, filename, raw OCR text, raw local finder message, editable citizen form value, or Procedure Intelligence administration is sent or persisted.

The assistant may answer an explicit cross-service match or the ambiguous unqualified address-change request inside the Kerala pension journey before provider invocation. Such a response uses `status: "ok"` with `selection.state: "clarification"`; every offered service comes from the active verified registry, and no separate pension-record address-change procedure is implied. The frontend renders the latest structured response once rather than duplicating the same assistant text from its bounded in-memory transcript.

`GET /api/v1/health` returns `{"status":"ok"}`. `GET /api/v1/public-config` returns application name, kiosk mode, AI availability, fixed `agent_provider`/`agent_model`, and bounded effective `inactivity_timeout_seconds`/`inactivity_warning_seconds`. Availability is true only when the server feature flag, allowlisted provider/model, and secret are present. No key, credential detail, provider error/diagnostic, or citizen state is public. Both return JSON with `Cache-Control: no-store`.

The catalogue, procedure detail, and readiness endpoints accept optional `locale=en|hi|ml`; omission remains backward-compatible English. Any other value returns generic `422 {"error":"Invalid request"}`. Localized responses include `locale` and `translation` metadata (`canonical_locale`, method, review status, and disclaimer). English is canonical verified content. Hindi and Malayalam are machine-assisted prototypes requiring native review; linked official wording prevails.

`GET /api/v1/procedures` returns `{ locale, translation, procedures: ProcedureSummary[] }`. This is the narrow browser matching catalogue: a summary contains only `service_id`, localized `title`, `short_description`, pack-authored `intent_phrases`, language-neutral `category`, localized `category_label`, `trust_state` (`current` or `stale`), and boolean `attention_required`. The attention flag is derived from unresolved structured fact conflicts and is independent of freshness. Only active validated packs are listed; procedure facts, readiness content, sources, provenance, handoff URLs, and other internal-pack material are not included in summaries. The browser uses this response only for deterministic local matching and never submits the raw citizen query.

`GET /api/v1/procedures/{service_id}` returns one localized `ProcedureDetail` with:

- locale/identity/trust: `locale`, `translation`, `service_id`, localized `title`, `short_description`, language-neutral `category`, localized `category_label`, `jurisdiction`, `department`, `official_publisher`, `interaction_modes`, `pack_version`, `pack_digest`, `last_verified_at`, `review_due_at`, `trust_state`, `attention_required`, and bounded `monitoring` trust metadata distinguishing one-shot prototype availability, baseline review status, continuous-monitoring false, and required human review;
- guidance: cited `requirements`, cited `required_documents`, `fee`, ordered cited `steps`, cited `submission_channels`, optional cited `tracking_guidance`, cited `limitations`, and optional cited `additional_review_items` for conditions Sahayi does not ask about or infer;
- handoff/provenance: HTTPS `official_handoff_url`, official `sources`, and the fact-key-to-source-ID `provenance` map.

Nested cited records include stable IDs, plain-text guidance, and non-empty `source_ids`. Fee contains `verification_status` (`confirmed`, `conflicting`, `free`, or `not_stated`), canonical decimal-string-or-null `amount`, canonical three-letter-or-null `currency`, `display_message`, `claims`, optional `resolution_guidance`, and aggregate `source_ids`. Each claim contains its decimal-string `amount`, three-letter `currency`, plain-text `qualifier`, and `source_ids`. A conflicting fee has null canonical amount/currency, at least two differently valued claims, and resolution guidance; a confirmed fee has agreeing claims and a canonical amount/currency. `attention_required` is true for a conflicting fee in both summary and detail responses. Source records contain `source_id`, `publisher`, `title`, HTTPS `url`, `retrieved_at`, optional `official_updated_date`, optional recorded `sha256`, and `source_type` (`webpage` or `pdf`).

An unknown service returns `404 {"error":"Procedure not found"}`. An unavailable/invalid active registry returns `503 {"error":"Procedure guidance is unavailable"}`. Errors are generic JSON with no stack trace, filesystem path, or environment detail. All API responses retain `Cache-Control: no-store`. Development CORS permits only the exact configured Vite origin; production uses same-origin `/api/v1` requests. Public config and procedure responses must never contain secrets or citizen data.

`POST /api/v1/procedures/{service_id}/readiness/evaluate` accepts exactly `{ "answers": { question_id: boolean | integer | option_id } }`. The answer map is bounded, unknown fields and question IDs are rejected, and every value is strictly revalidated against the active pack. Strings are never coerced into booleans or integers. The endpoint is stateless, performs no retry or external call, does not log or echo answers, and returns generic `404`, `422`, or `503` errors.

The readiness response contains `locale`, `translation`, `pack_version`, `pack_digest`, `evaluation_status`, `complete`, adaptive `progress`, the localized next applicable question or resolved outcome, a stable-ID `reason_trace`, localized official source labels, recommended next steps, an unchanged HTTPS official handoff, and a localized non-approval disclaimer. Question IDs, option IDs, rule/outcome selection, source IDs, URLs, and factual values are invariant across locales. A sensitive question remains a closed category choice, not an identifier or exact value. A complete outcome status is `ready`, `alternative_path`, `needs_information`, or `cannot_confirm`. The frontend keeps locale, answer map, and Back history in React memory only and sends the complete map on each evaluation.

`POST /api/v1/procedures/{service_id}/checklist?locale=...` accepts the same exact bounded readiness answer map and returns a deterministic `PersonalizedChecklist`: preliminary result, ready facts, documents, confirmations, ordered steps, warnings, channels, official sources, unverified scope, pack version/digest, HTTPS handoff, and non-approval disclaimer. Every item retains source IDs. `POST /api/v1/procedures/{service_id}/synthetic-form-assistance?locale=...` accepts only an optional allowlisted synthetic `persona_id` and returns a watermarked preparation worksheet with fictional closed answers, localized field explanations, private/not-collected handling, reference status, source IDs, and official sources. Neither endpoint calls AI, accepts citizen free text/files, stores state, or creates a server file.

`POST /api/v1/procedures/{service_id}/demo-submission?locale=...` accepts exactly an allowlisted bundled `persona_id` and `scenario_id` (`normal-completion` or `action-required`). `POST /api/v1/procedures/{service_id}/demo-status?locale=...` additionally accepts the exact deterministic `DEMO-...` reference and one status enum. Responses contain a localized synthetic disclosure/disclaimer, current status, deliberately ordered timeline, clearly simulated relative labels, next action, and source IDs only where a preparation fact is cited. The contract rejects unknown personas, real-looking references, statuses outside the selected sequence, extra fields, and free text. It is stateless and performs no official call, submission, approval, or tracking.

`POST /api/v1/assistant/turn` remains the detailed secondary AI boundary. `POST /api/v1/conversation/turn` may call the same adapter once only for a `cloud_clarification` event with literal consent and a bounded PII-screened message; the validated assistant result then becomes bounded LangGraph input, while clear local matches never use Groq. The first Chat Completions request contains only the fixed model, bounded validated system/history/current-user messages, the application-selected node's zero-argument function subset (no more than two), automatic tool choice, disabled parallel calls, zero temperature, disabled streaming, and the bounded completion limit. Locale, confirmed service, validated readiness answers, selected persona, and demo status are server-bound into the unchanged canonical executor and cannot be supplied by Groq. Each tool call is validated and executed locally; only its reconstructed assistant tool-call message and matching documented tool-result message continue the bounded loop. That final request contains no tools and sets `tool_choice="none"`. The final JSON text must pass the strict server model before any citizen response is assembled. Both public paths reject arbitrary metadata, files, OCR text, invalid IDs/actions, missing consent, greetings and obvious gibberish before Groq, and never expose raw provider output, arguments, prompts, provider IDs, internal errors, or model-authored URLs.

The frontend keeps AI consent/conversation and all deterministic workflow outputs in React memory only. Language change clears the conversation and relocalizes active deterministic views. Start Over and persistent End session abort all tracked fetches and clear consent, conversation, service query/match, selection, readiness answers/history/outcome, checklist, worksheet/persona, demo reference/status, and navigation; End session adds a localized confirmation. The same operation runs after the configurable inactivity warning expires, using elapsed time when a hidden tab becomes visible. No browser storage is used. The UI names GroqCloud, states that Groq collects usage metadata, and explains that Zero Data Retention is an owner-controlled Groq Console setting that Sahayi code cannot enable or guarantee.

No official write, real application submission/status lookup, live form filling, OTP, database, durable session, analytics, telemetry, server file upload, admin mutation endpoint, continuous monitoring, or hosted source retrieval is implemented; do not infer those contracts. Browser-local printed-text OCR and browser-dependent voice are optional progressive enhancements only.
